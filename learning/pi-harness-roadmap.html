Pi Harness 研习路线

对一个 coding agent 来说，模型只提供决策，harness 提供其余的一切：循环、工具、上下文预算、会话状态、错误恢复、扩展点。 对 Claude Code 的公开分析里有一个常被引用的比例——约 1.6% 的代码在处理 AI 决策逻辑，98.4% 是运行时基础设施； 同一个模型换一套 harness，基准分能相差十几个百分点。这份路线用十个阶段带你把 Pi 这套 harness 从外到内拆开。

面向 harness 新手 / 有 TypeScript 基础 总时长 约 16–24 天（每天 2–3 小时） 形式 读源码 → 动手改 → 自检 → 对照业界 产出 一个自己的 mini harness

为什么拿 Pi 当教材

市面上能学的 harness 有三类：Claude Code 闭源，只能靠逆向分析；Codex CLI 开源但用 Rust 写，且深度绑定 OpenAI 自家形态； DeepSeek Harness 走的是「一切皆插件」的极端可组合路线，抽象层多，对新手不友好。

Pi 的价值在于它刚好处在可通读的规模：核心循环 agent-loop.ts 只有 794 行， 分层边界清晰（ai → agent → coding-agent），文档就写在仓库里而不是官网上， 还配了 SDK 示例和 evals。你能在两三周内把一整条链路——从 HTTP 请求到终端里那一行字——完整走通，这在别的 harness 上很难做到。

更实际的一点：Pi 的 AGENTS.md 明确写着「核心保持小，能力靠扩展长出来」。 这意味着你读到的每一处复杂度，几乎都是被现实逼出来的，而不是架构洁癖。这正是学 harness 最需要的东西。

先建立分层心智模型

整份路线只围绕一个骨架展开。在读任何一行代码之前，先把这张图记住：越往下越无状态，越往上越有状态。 新手最容易犯的错，就是把上层的职责（会话、压缩、权限）错当成下层的问题去找。

十个阶段

每个阶段都是同一个结构：核心问题 → 读什么 → 动手 → 自检 → 业界对照。 「读什么」里的行号对应仓库当前状态（v0.84.4），改动后可能漂移几行，按函数名找即可。

建立地图

半天

核心问题：harness 到底包含什么？Pi 的九个包各自的边界在哪里？

读什么

  • README.md包清单、开发命令、供应链加固策略
  • AGENTS.md项目铁律。注意「核心保持小、能力靠扩展」这条设计取向
  • packages/coding-agent/docs/index.md全部文档的入口，先扫一遍标题建立索引
  • package.json看 build 脚本——它的顺序就是包依赖顺序：tui → telemetry → ai → agent → sqlite → protocol → client → server → coding-agent

动手

  • npm install --ignore-scripts 然后 npm run build。
  • ./pi-test.sh 从源码跑起来，随便问一句，看它调了哪些工具。
  • 把 build 脚本的顺序抄成一张依赖图，标出每个包「对谁负责」。这张图后面九个阶段都要用。

自检

  • 要新增一个 provider，改哪个包？要新增一个工具呢？要改压缩策略呢？
  • packages/agent 和 packages/coding-agent 的分界线是什么？为什么前者根本不认识「文件」和「bash」？
业界对照 所有 harness 都可归结为四件必要设施：agent loop、tool interface、context management、control mechanisms。 读 Pi 时随时问自己：眼前这段代码属于哪一件？

Agent Loop：把无状态 API 变成 Agent

1–2 天 · 最关键一站

核心问题：LLM 的 HTTP 接口是无状态的「context in → tokens out」。到底是什么把它变成了一个能连续干几十步活的 agent？

答案就是一个循环。但真实的循环不止「调模型 → 执行工具 → 再调模型」这么简单——Pi 用了嵌套的两层，各自消费一种不同的队列。

读什么

  • packages/agent/README.md先读完「Event Flow」整节。事件序列比源码更快建立直觉
  • agent-loop.ts:171while (true) 外层；:175 内层。上面那张图就是这两行
  • agent-loop.ts:172hasMoreToolCalls = true 初值为真——保证内层至少跑一轮
  • agent-loop.ts:212streamAssistantResponse()，唯一调用 LLM 的地方
  • agent-loop.ts:284该函数内部：transformContext → convertToLlm → 组 Context → 解析 API key → 消费流
  • agent-loop.ts:230务必细读。stopReason === "length" 时整批 tool call 直接判错
  • agent-loop.ts:235hasMoreToolCalls = !terminate——只有整批都 terminate 才提前收工
  • agent-loop.ts:409 / 487并行与串行两种执行策略，以及单个工具如何把整批拉回串行
  • packages/agent/src/agent.tsAgent 类：在裸循环之上加状态、订阅、abort、队列管理

动手

  • 不看 Pi，用 @earendil-works/pi-ai 手写一个 60 行的最小循环：prompt → stream → 有 toolCall 就执行 → 结果塞回 messages → 再来一轮。给它一个 read_file 工具就够。
  • 写完后逐行对照 agent-loop.ts，列出 Pi 多做的事。至少能列出十条：事件发射、steering、follow-up、terminate、截断保护、并行执行、abort 传播、apiKey 动态解析、context 转换钩子、回合前准备。
  • 把 agent-loop.ts:230 那个截断保护临时删掉，构造一个 maxTokens 极小的请求，看会发生什么。

自检

  • steering 和 follow-up 分别在循环的哪一行被消费？为什么必须放在不同层？
  • 为什么 terminate 要求「整批工具结果都 terminate」才生效，而不是任意一个？
  • agentLoop() 和 agentLoopContinue() 的区别是什么？后者为什么要求最后一条消息不能是 assistant？
  • 响应被 token 上限截断时，为什么参数能解析成功也不能执行？
业界对照 这个结构就是 ReAct（reason + act）循环的工程化版本：plan → act → observe → loop。 OpenAI 那篇《Unrolling the Codex agent loop》讲的是同一件事，但 Codex 走的是 reasoning loop 与 tool execution 解耦的分离式架构（为了 Zero Data Retention 做无状态请求）； Pi 把两者放在同一进程里，换来的是更简单的事件模型和更好的可读性。

Provider 抽象层

1–2 天

核心问题：三十多家 provider 的流式协议、tool call 格式、thinking 参数、计费字段全都不一样。怎么归一成一套接口，又不丢失各家的特性？

读什么

  • packages/ai/README.md目录就是这一层的能力清单：auth 解析、tools、image、thinking、stop reason、跨 provider 交接
  • packages/ai/src/types.tsContext / Message / Usage / StopReason。整个 Pi 的公共词汇表
  • src/api/anthropic-messages.ts对照 src/api/openai-responses.ts：同一套事件流的两种实现
  • src/providers/faux.ts测试用假 provider。想快速看清接口边界，读它最省时间
  • src/api/transform-messages.ts跨 provider 交接时消息如何改写
  • src/models.generated.ts只读不改。要改去改 scripts/generate-models.ts 再重新生成

动手

  • 用 faux provider 写一个不花钱的测试，跑通一次完整的 tool call 往返。
  • pi --list-models，然后在源码里找到这个列表是怎么拼出来的。
  • 数一遍流式事件的类型：start / text_* / thinking_* / toolcall_* / done / error，并说明为什么每个事件都带一个 partial 字段。

自检

  • stream() 和 streamSimple() 的分工是什么？agent 层用的是哪个，为什么？
  • 为什么 thinkingLevel 抽象成 off / minimal / low / medium / high / xhigh / max，而不是直接传 token 预算？
  • tool call 的参数是流式到达的。如果流到一半断了，Pi 怎么处理这「半个 JSON」？（提示：best-effort 抢救解析，然后被阶段 01 的截断保护兜住）
业界对照 DeepSeek Harness 把这层做得更激进——连 model adapter 本身都是插件，「没有需要打补丁的特权内核」。 Pi 的选择是保留一个稳定内核 + createProvider() 扩展口。两种取舍各有代价：前者灵活但抽象层厚，后者简单但内核改动成本高。

工具层：Agent-Computer Interface

2 天

核心问题：工具描述写得好不好，直接决定 agent 的行为质量。「好」的具体标准是什么？

这个阶段有一处 Pi 特有的巧思值得注意：工具自带 system prompt 片段。 edit.ts 里导出的 editToolSystemPromptContribution 含一个 snippet 和一组 guidelines， 装配 system prompt 时按实际启用的工具动态拼进去。换句话说——是工具决定 prompt，而不是 prompt 里硬编码工具。 禁用某个工具，相关的指导语会自动消失。

读什么

  • src/core/tools/index.ts八个内置工具的注册表。注意 createCodingTools() 默认只给四个：read / bash / edit / write
  • tools/read.ts:218description 里明确写了截断规则和 offset/limit 续读协议——把「怎么用」直接写给模型看
  • tools/edit.ts:56editToolSystemPromptContribution，上面说的那个机制
  • tools/edit.ts:45schema 里的约束：每个 oldText 对原文匹配、必须唯一、不许重叠
  • tools/truncate.ts配合 tools/output-accumulator.ts：工具吐多少字节是 harness 说了算，不是命令说了算
  • tools/file-mutation-queue.ts并行执行下同一文件的写冲突串行化
  • tools/bash.ts进程生命周期、超时、abort、spawn hook（沙箱扩展点就在这里）

动手

  • 写一个自定义工具（用 extension 形式，见阶段 06 的写法）。先把 description 写得含糊，跑几轮；再按 Anthropic 的工具写作原则改好，对比模型的调用准确率。
  • 把 read 工具的默认截断行数改到 20，观察模型会不会自己用 offset 续读——这就是在验证「description 即协议」。
  • 在 bash 工具里加一行日志，打出每次实际执行的命令，跑一个真实任务，看模型的命令构造习惯。

自检

  • 工具失败为什么必须 throw 而不是 return 一段错误文本？（提示：agent 捕获后置 isError: true，模型看到的语义不同）
  • read 和 bash + cat 功能重叠，为什么还要单独做一个 read？
  • 如果一次 assistant 回复里有三个 edit 调用改同一个文件，会发生什么？
业界对照 Anthropic 的工具设计三原则——职责不重叠、自包含且能容错、描述本身就是 prompt 工程。 另一个极端参考：DeepSeek Harness 的 minimal 预设只给两个工具（bash 和 str_replace_editor）。 读完这一阶段可以想想：Pi 的八个工具里，哪几个其实是 bash 的特化？特化换来了什么？

上下文工程与压缩

2 天 · 第二难点

核心问题：上下文窗口是一笔有限预算。谁在花？怎么花？花光了怎么办？

先看「怎么花」。buildSystemPrompt() 的拼装顺序是固定的： 工具清单 → guidelines（由启用的工具决定）→ appendSystemPrompt → <project_context>（AGENTS.md 等）→ 技能索引 → 当前工作目录。 每一段都在抢同一份预算。

读什么

  • src/core/system-prompt.ts:28buildSystemPrompt()，拼装顺序全在这一个函数里
  • docs/compaction.md先读文档再读代码。里面那张 ASCII 图和上面这张说的是同一件事
  • core/compaction/compaction.ts:235shouldCompact()：contextTokens > contextWindow − reserveTokens
  • compaction.ts:128默认值：reserveTokens 16384、keepRecentTokens 20000
  • compaction.ts:388从最新往回累加 token 找切点的算法
  • compaction/utils.ts重点。读过／改过的文件列表被单独抽出来跨压缩累积——摘要可以丢细节，文件清单不能丢
  • agent-loop.ts:284再看一次 transformContext → convertToLlm 这条管线，现在你知道它为谁服务了

动手

  • 把 ~/.pi/agent/settings.json 里的 reserveTokens 调到很大（比如上下文窗口的一半），跑个任务让自动压缩尽快触发。
  • 压缩前后各存一份 session JSONL，diff 一下——确认原始条目一条都没少。
  • 用 /compact 只保留和构建脚本相关的内容 这样的自定义指令跑一次，对比摘要差异。

自检

  • 为什么压缩要保留 firstKeptEntryId 指针，而不是直接把旧条目删掉？（至少能说出三个理由）
  • 为什么「读过哪些文件」要脱离摘要单独累积传递？丢了会出什么问题？
  • 压缩本身也要调一次 LLM。这次调用的 session id 和 prompt cache 策略为什么要和主会话区别对待？
  • 启用／禁用一个工具，system prompt 会变。这对 prompt cache 命中率意味着什么？
业界对照 Codex CLI 区分 pre-turn 和 mid-turn 两种压缩时机：前者在用户新回合前跑并清掉引用上下文，后者在工具执行途中撞到上限时跑。 Pi 的触发点在三处：新 prompt 前、工具批次完成后的回合间、以及一次 agent run 结束后。 Anthropic 那篇《Effective context engineering》里的一句话值得抄下来：目标是找到最小的高信号 token 集合。

会话状态与分支树

1–2 天

核心问题：agent 会话不是线性对话，而是一棵可以回溯、分叉、重跑的树。用 append-only 的 JSONL 怎么表达一棵树？

读什么

  • docs/session-format.md完整的条目类型清单和文件位置约定
  • core/session-manager.ts:46SessionEntryBase 的 id / parentId——树就靠这两个字段
  • session-manager.ts:143SessionEntry 联合类型：消息、压缩、分支摘要都是条目
  • session-manager.ts:230v1 → v2 迁移：给旧的线性序列补上 parentId。读这段能彻底理解树的设计动机
  • session-manager.ts:356沿 parentId 回溯组装当前分支的上下文
  • compaction/branch-summarization.ts切分支时如何保住上下文
  • docs/sessions.md/tree、/resume、fork 的用户侧语义

动手

  • 写一个脚本解析 ~/.pi/agent/sessions/**/*.jsonl，统计每个会话的 token 用量、成本、工具调用分布。这是理解条目结构最快的方式。
  • 在交互模式里用 /tree 回到几步之前，换个说法重跑，然后在 JSONL 里找到这次分叉——确认没有新建文件，只是多了一条 parentId 指向旧节点的条目。

自检

  • append-only 的文件如何做到「原地分支」而不复制？「当前分支」是怎么确定的？
  • 为什么压缩条目和分支摘要条目要和消息条目放在同一个序列里，而不是单独存？
  • session 版本从 v1 到 v3 各解决了什么问题？如果你要加 v4，会怎么做？
业界对照 会话持久化是各家 harness 差异最大的地方，也最能看出产品取向： 纯线性追加（简单、够用）vs 树形分支（能回溯、能对比不同路线）。 Pi 选了后者，代价是压缩、上下文组装、UI 全部要按树来写。做自己的 harness 时，这是第一个要想清楚的取舍。

扩展、技能与包

2–3 天

核心问题：harness 核心要小，能力要能长出来。扩展点该开在哪、开成什么形状？

这里有整份路线最值得抄走的一个设计：技能的渐进式披露。 formatSkillsForPrompt() 只往 system prompt 里放每个技能的 name、description 和文件路径——三行。 真正的技能内容留在磁盘上，等模型判断任务匹配了，自己用 read 工具去加载。 一百个技能常驻上下文的成本，就这样被压到几百 token。

读什么

  • docs/extensions.md通读。这是全仓库信息密度最高的一篇文档
  • core/extensions/types.ts:1298tool_call 事件——可以 block 也可以改参数，权限门禁就建在这里
  • core/extensions/types.ts:1267session_before_compact：连压缩策略都能被扩展接管
  • core/extensions/runner.ts配合 loader.ts：扩展的发现、加载、执行顺序、错误隔离
  • core/skills.ts:355formatSkillsForPrompt()，上面说的那三行
  • docs/skills.mdPi 实现的是公开的 Agent Skills 标准，不是私有格式

examples/extensions/ 下有七十多个可运行示例，至少精读这五个：

  • permission-gate.ts拦截危险命令，最典型的 tool_call 用法
  • custom-compaction.ts把阶段 04 的策略换成自己的
  • subagent/在工具里嵌套一个完整 agent——多智能体的最小实现
  • plan-mode/用扩展改变整个交互模式
  • git-checkpoint.ts每回合打快照，分支时回滚。状态管理的实战

动手

  • 写一个 permission gate：拦住 rm -rf 和 sudo，弹确认框。放到 .pi/extensions/ 里用 /reload 热加载。
  • 写一个技能（仓库里就有现成参照：.pi/skills/add-llm-provider.md）。然后用 /debug 看它在 system prompt 里到底占了几行。
  • 写一个自定义工具 + 一个自定义命令，体会 registerTool 和 registerCommand 的区别：前者给模型用，后者给人用。

自检

  • extension / skill / prompt template / 自定义工具，四者分别解决什么问题？为什么不能互相替代？
  • 技能内容不进 system prompt，模型怎么知道该读它？如果模型不读会怎样？
  • 项目级扩展（.pi/extensions/）为什么必须等项目被信任后才加载？
业界对照 DeepSeek Harness 走到了另一端——界面、工具调用、agent loop 本身全部是插件，「没有特权内核」。 Claude Code 则是分层的：hooks 管拦截、skills 管知识、MCP 管外部集成。 Pi 的位置在中间：内核稳定，但扩展能碰到几乎所有生命周期事件。做取舍时问自己：改一个行为，你希望需要读多少代码？

交互层与嵌入方式

1–2 天

核心问题：同一个 AgentSession，怎么同时服务终端 UI、脚本、IDE 插件和服务端？

agent-session.ts 有 3500 行，不要通读。先看文件头那段注释（它明确列出了这个类承担的六项职责）， 然后按方法名跳读：prompt / steer / followUp / compact / navigateTree / bindExtensions。 这个类的存在意义就是：把「模式无关」的逻辑收拢在一处，让四种 I/O 层各自只写自己的部分。

读什么

  • core/agent-session.ts:1文件头注释。六项职责，一句一项
  • core/agent-session.ts:1160prompt()，从用户输入到 agent 启动的完整路径
  • modes/index.ts三种运行模式的出口：interactive / print / rpc
  • packages/tui/README.md差分渲染、CSI 2026 同步输出、bracketed paste。终端 UI 的工程难点
  • docs/sdk.md配合 examples/sdk/01…13：从 01-minimal.ts（十行起一个会话）按序跑到 13-session-runtime.ts
  • docs/rpc.md配合 docs/json.md：给 IDE 和脚本用的两种结构化接口
  • packages/protocol/README.md四字节长度前缀 + CBOR。实验性的服务端协议

动手

  • 按序跑完十三个 SDK 示例，每个都改一处再跑。这是把前六个阶段串起来的最好方式。
  • 用 pi -p "..." 的 print 模式 + JSON 事件流驱动一次任务，把事件流存下来画个时序图。
  • 照 AGENTS.md 里的 tmux 方法跑一次交互模式，用 tmux capture-pane 抓屏——顺便学会怎么自动化测试 TUI。

自检

  • AgentSession 相比裸 Agent 多承担了哪些职责？为什么这些不放进 packages/agent？
  • 为什么要单独做 RPC 模式，print + JSON 事件流不够吗？
  • 差分渲染为什么对 agent CLI 特别重要？（提示：流式 token + 每秒多次重绘）
业界对照 Codex 把 reasoning loop 和 tool execution 拆成两端，好处是能做无状态请求、满足 Zero Data Retention。 Pi 的 protocol / client / server 三个包正在往类似方向探索（标注为 experimental）。 如果你要做的是「本地跑但远程可观测」的产品形态，这三个包值得单独花时间。

评测、安全与运维

1–2 天

核心问题：你改了 prompt、换了工具描述、调了压缩阈值。怎么证明这是进步而不是退步？

读什么

  • packages/evals/README.md把真实 AgentSession 接进 vitest-evals，在隔离的临时目录里跑
  • packages/evals/src/pi-harness.tsharness 配置项：换模型、换工具集、换技能，都能做成对照组
  • packages/telemetry/README.md厂商中立的遥测契约 + 一致性测试
  • docs/security.md配合 SECURITY.md：威胁模型。注意 Pi 刻意不内置权限系统
  • docs/containerization.md三种沙箱方案：Gondolin 微 VM / Docker / OpenShell
  • core/trust-manager.ts项目信任门禁——未信任的项目不加载其扩展和技能
  • README.md供应链一节：依赖锁定、min-release-age=2、shrinkwrap 校验。这也是 harness 的一部分

动手

  • 写一个 eval：同一个任务，两版 system prompt，跑十次看差异。这会立刻改变你对「prompt 调优」的感觉。
  • 把阶段 03 里改坏的工具描述做成对照组，用 eval 量化它到底差多少。
  • 按 containerization.md 用 Docker 跑一次 Pi，感受权限边界在哪。

自检

  • 为什么 Pi 不内置权限系统，而是把边界推给容器？这个决定的代价是什么？
  • evals 和单元测试的区别是什么？为什么 evals 必须用真模型，而 suite 测试要用 faux provider？
  • 项目信任机制防的是什么攻击？（提示：clone 一个仓库，它的 .pi/extensions/ 里有代码）
业界对照 这是最容易被跳过、也最能拉开差距的一环。「同一个模型换 harness 差十几个百分点」这个结论， 正是靠这类可复现的评测得出来的。没有 evals，你对 harness 的所有改动都只是在凭感觉。

毕业项目：造一个 mini harness

3–5 天

核心问题：你真的懂了吗？唯一的验证方式是自己造一个，然后数一数你省略了什么。

目标：300 行以内，包含五件事

  • 循环——单层就行，但必须正确处理 stopReason 的每一种取值。
  • 三个工具——read / bash / edit，带截断和错误抛出。
  • 压缩——超过阈值就摘要，保留最近 N token，记住读过的文件。
  • 持久化——JSONL 追加，能 resume。树可以先不做。
  • 一个扩展点——工具执行前的拦截钩子，能 block。

然后做这件更重要的事

把你的 300 行和 Pi 逐项对照，列一张「我省略了什么 / 代价是什么」的表。 比如：没做 steering（用户无法打断）、没做并行工具（慢一倍）、没做截断保护（会执行半个命令）、 没做 abort 传播（Ctrl-C 杀不掉子进程）、没做文件写队列（并发改同一文件会丢改动）。

这张表就是你对 harness 工程的真实理解。它比任何笔记都值钱。

进阶

  • 给 Pi 提一个 PR。先读 CONTRIBUTING.md——新贡献者的 issue 和 PR 默认会被自动关闭、由维护者每天人工复核，所以质量门槛要按最高标准来。
  • 用阶段 08 的 evals 给你的改动做量化证明，附在 PR 里。

五个常见误区

  • 01

    一上来就读 agent-session.ts（3500 行）。

    先读 agent-loop.ts（794 行）。前者是后者的装配层，不理解循环就看不懂装配。

  • 02

    以为 harness 的难点在 prompt 写作。

    难点在错误处理、输出截断、并发写冲突、中断传播、状态恢复。翻一遍 agent-loop.ts 里的注释就明白了——注释几乎全在解释边界情况。

  • 03

    直接改 packages/ai/src/models.generated.ts。

    它是生成产物。改 packages/ai/scripts/generate-models.ts 再重新生成——AGENTS.md 里明确写了这条。

  • 04

    用真 API key 跑测试，烧钱又不稳定。

    套件测试用 test/suite/harness.ts + faux provider；只有 evals 才需要真模型。根目录跑 ./test.sh 会自动跳过依赖 LLM 的测试。

  • 05

    改完就发，靠感觉判断变好了。

    先写 eval 再改代码。harness 的很多改动是「这里好了那里坏了」，凭感觉必然翻车。
